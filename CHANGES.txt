KASHMIRMENU - CHANGE LOG
========================
Covers all work done in this session, in two phases:
  Phase 1 - Production readiness of the existing Spring Boot backend
  Phase 2 - New React frontend, plus the backend changes it required

This log was compiled from the session's edit history and file timestamps (the
project is not a git repository, so there is no diff to check against). Items
marked [NOT VERIFIED] were not exercised in this environment.


--------------------------------------------------------------------------------
PHASE 1 - PRODUCTION READINESS (BACKEND)
--------------------------------------------------------------------------------

1. Security hardening
   - JWT secret validation: JwtProperties now fails fast at startup if the secret
     is missing or shorter than 32 bytes (no insecure fallback).
   - JwtAuthenticationFilter: handles invalid/expired tokens (JwtException) with
     logging instead of letting them surface as server errors.
   - GlobalExceptionHandler: added handlers for BadCredentialsException and
     authentication errors. Login failures return 401 with a generic message
     ("Invalid email or password.") so the response does not reveal whether an
     account exists.
   - CORS: new CorsProperties + CorsConfig. Allowed origins come from
     CORS_ALLOWED_ORIGINS. Fails closed (no origins) if unset in prod.
   - WebSocketConfig: STOMP endpoint /ws now uses the configured allowed origins
     instead of a wildcard.
   - Rate limiting: new RateLimitProperties and AuthRateLimitFilter, a per-IP
     limiter on /api/v1/auth/**. X-Forwarded-For is only trusted when
     TRUST_FORWARDED_HEADER=true.
   - SecurityConfig: rewritten with stateless sessions, explicit public routes,
     JSON 401/403 responses, and the rate-limit filter in the chain.
   - Role seeding: new migration V16__seed_missing_roles.sql. The RoleName enum
     had roles that no migration inserted, so registering an owner failed on a
     fresh database.
   - User.restaurant made nullable (and CustomUserDetails.getRestaurantId made
     null-safe) so ADMIN/CUSTOMER users without a restaurant work.

2. Operational readiness
   - Spring profiles: application.yaml (shared), application-dev.yml,
     application-prod.yml, application-test.yml. No environment-specific values
     are hardcoded; everything is driven by environment variables.
   - Production profile: Swagger UI and /v3/api-docs disabled; JWT_SECRET and
     CORS_ALLOWED_ORIGINS have no defaults, so the app refuses to start without
     them.
   - Actuator added (build.gradle). Liveness/readiness health endpoints are
     public; other endpoints are not exposed.
   - RequestIdFilter + WebFilterConfig: every request gets an X-Request-Id
     (generated if absent), echoed on the response and put in log lines.
   - Graceful shutdown enabled.

3. Test coverage (H2 in-memory database, "test" profile)
   - build.gradle: added H2 as a test runtime dependency.
   - application-test.yml, src/test/resources/data.sql (seeds roles).
   - KashmirmenuApplicationTests (context loads)
   - AuthControllerIT (4 tests)
   - SecurityAccessIT (4 tests)
   - JwtServiceTest (3 tests)

4. Containerization and CI/CD
   - Dockerfile and .dockerignore for the backend image.
   - docker-compose.yml: MySQL + app. Required secrets (DB_PASSWORD,
     DB_ROOT_PASSWORD, JWT_SECRET) fail with a clear message if unset.
   - .env.example documenting every variable.
   - .gitignore: ignores .env files (keeps .env.example).
   - .github/workflows/ci.yml: build + test on push/PR to main, upload test
     reports, then build the Docker image (no push).
   - README.md: configuration table, operability notes, testing, CI/CD.

KNOWN GAPS AND THINGS NOT VERIFIED
--------------------------------------------------------------------------------
 1. Coupons are stored/managed but NOT applied to cart or order totals (the
    existing apply endpoint only increments a counter). The admin page says so;
    the diner UI deliberately has no coupon box.
 2. The websocket (/topic/restaurants/{id}) is unauthenticated: anyone who knows a
    restaurant id can subscribe to its notification messages.
 3. Coupon, notification and inventory endpoints have no role guards, and coupons
    and notifications accept restaurantId from the client (possible cross-tenant
    access). A full authorization audit has NOT been done.
 4. No payment gateway. A diner's payment choice creates a PENDING payment; staff
    mark it paid/failed manually.
 5. No staff-creation endpoint, so chef/waiter/manager accounts cannot be created
    through the API.
 6. Anyone holding a table's QR code can order for that table, and the cart is
    shared by everyone at the table. Deactivating/deleting the table revokes it.
 7. The rate limiter is in-memory and per instance.
 8. [NOT VERIFIED] The frontend has not been run end to end against a live backend
    or in a browser. A live test was attempted but could not run (H2 is a
    test-only dependency and the dev profile needs MySQL). Endpoint paths and
    response shapes were checked against the controllers by reading them.
 9. [NOT VERIFIED] Neither Docker image has been built here, and docker-compose
    has not been started. The new CI workflow has not run.
10. [NOT VERIFIED] The earlier "production ready" backend work was verified through
    the automated tests only, not by deploying it.
11. Flyway migrations were validated only indirectly (tests use H2 with Hibernate
    schema generation and Flyway disabled). Run the app once against a real
    MySQL to confirm V16 and the schema validate cleanly.

Files in the folder that were NOT changed by this work: .idea/* and

PHASE 3 - PAYMENTS & REVENUE ANALYTICS
--------------------------------------------------------------------------------

Goal: separate tracking of Cash / UPI / Card / Wallet, with UPI and wallet broken
down by app (Google Pay, PhonePe, Paytm UPI, Paytm Wallet, ...), plus a premium
analytics page, payment history and daily reconciliation.

The existing payment model could not express any of this: payments.order_id was
UNIQUE (one payment per order, so no split bills), there was no provider, no refund
record, no payment timestamp of its own, and no business time zone. Phase 3 is
mostly about fixing that foundation; the dashboard then follows from it.


1. Data model (migration V18__payment_split_refunds_reconciliation.sql)
   - payments: dropped the UNIQUE on order_id (kept a plain index for the FK), so an
     order can have several payments - split bills, and retries after a failure.
   - payments: added restaurant_id (denormalised for indexed per-restaurant
     aggregation), payment_provider, card_type, currency, payment_timestamp,
     idempotency_key, recorded_by_user_id, settled_at. Indexes on
     (restaurant_id, payment_timestamp) and (restaurant_id, payment_status,
     payment_timestamp); unique (restaurant_id, idempotency_key).
   - New table payment_refunds: many partial refunds per payment, each linked to the
     original payment, with amount, reason, date and who issued it.
   - New table cash_reconciliations: per-day cash counts (expected, counted,
     difference, note, who counted).
   - Backfill is non-destructive: restaurant_id from the order, payment_timestamp
     from paid_at/created_at. No provider is invented - historical rows keep NULL and
     are reported as "Unknown". Every pre-existing REFUNDED payment gets one full
     refund record so net collections stay correct (dated by updated_at, the only
     information available - see README known limitations).

2. Enums
   - PaymentMethod: added BANK_TRANSFER, GIFT_CARD, STORE_CREDIT, VOUCHER, OTHER, and
     metadata (label, cash?, digital?, diner-selectable?, has providers?). Adding a
     method is now a one-line change that flows through to the API and dashboard.
   - New PaymentProvider (parent method + label) and CardType (kind only, never a
     card number).
   - PaymentStatus: added CANCELLED and PARTIALLY_REFUNDED, plus a CAPTURED set that
     defines, in one place, what counts as money received.

3. Payment rules (PaymentServiceImpl, rewritten)
   - Staff can record money received as 1..10 components in one request (split bill).
   - The order row is locked while payments change, so two staff members or a double
     click cannot overpay an order; an optional idempotency key makes a replayed
     request return the original result instead of recording twice.
   - Amounts are validated against what is actually outstanding.
   - A payment can only move out of PENDING, and repeating the same status change is a
     no-op (duplicate gateway callbacks are safe).
   - Refunds go through their own endpoint, are bounded by what is left on the payment,
     and set PARTIALLY_REFUNDED / REFUNDED automatically.
   - A provider must belong to its method (Paytm UPI is not a wallet); card type only
     applies to CARD. Nothing is ever inferred.
   - Taking payment at the counter cancels the diner's pending choice (kept on record,
     never counted as revenue).
   - SECURITY: the diner endpoint and the staff endpoint no longer share a request
     type. CreatePaymentRequest (public) still carries only a method; amounts,
     providers and "already paid" exist solely on the staff type. Counter-only methods
     are not offered to diners.

4. Analytics (new com.kashmirmenu.app.analytics package + PaymentAnalyticsQueries)
   - All aggregation is database-side: grouped rows by method/provider/hour, never a
     download of individual payments. JPQL is assembled from fixed fragments with
     named parameters only.
   - One pure calculator derives every panel from the same rows, so providers reconcile
     to their method, methods to the total, and the series and heatmap to both.
   - Period presets compare against the same elapsed slice of the previous period, so
     "today so far" is not compared with a whole yesterday.
   - Insight rules each state a minimum sample size and stay silent below it.
   - Half-open [start, end) date ranges and a configurable business time zone.

5. API
   - GET  /api/v1/payment-analytics/meta|overview|transactions|transactions/{id}
   - GET  /api/v1/payment-analytics/transactions/export        (CSV, 50k row cap)
   - GET  /api/v1/payment-analytics/reconciliation
   - POST /api/v1/payment-analytics/reconciliation/counts|settle
     All of the above: ADMIN / RESTAURANT_OWNER / MANAGER only.
   - POST /api/v1/payments/orders/{id}/collect        (cashiers and waiters too)
   - GET  /api/v1/payments/orders/{id}/summary
   - POST /api/v1/payments/{id}/refunds               (managers and owners only)
   - Order tracking now returns amountPaid and balanceDue, derived from all payments.
   - Dashboard "today's revenue" now uses the same definition as the new page
     (received minus refunds issued), instead of summing payment rows directly.
   - CSV cells starting with = + - @ are prefixed with an apostrophe (formula
     injection); only whitelisted columns can be sorted on.

6. Frontend
   - New page /admin/revenue: hero total with the method split, six KPI cards with
     previous-period comparison, insights, six charts (method donut, provider bars,
     revenue over time, payments over time, period comparison, weekday/hour heatmap),
     filters (period incl. custom range, method, provider, status, staff, grouping),
     payment history (search, sort, pagination, CSV, detail drawer with refunds), and
     the daily reconciliation panel.
   - Charts are hand-written SVG. No chart library was added: this bundle is also
     served to diners scanning a QR code.
   - Orders page: "Take payment" opens a split-capable dialog; confirming a diner's
     pending payment now asks which UPI app or card type it was. This is the change

   - Diner order page: shows part-paid balances and allows a retry after a failure.
   - styles.css: payment-method palette (green/violet/blue/gold, clear of the crimson
     primary, each always paired with a text label), tuned for the always-dark Chinar
     staff theme; the history table becomes amount-led transaction cards on phones.
   - New lib/charts.ts holds all chart geometry and formatting as pure functions.

7. Configuration
   - APP_TIMEZONE (default Asia/Kolkata) applied to both the app and the MySQL
     container, so stored timestamps and reporting agree. APP_CURRENCY (default INR).
   - Both documented in .env.example and the README.

PHASE 4 - COUPONS DINERS CAN ACTUALLY USE
--------------------------------------------------------------------------------

Reported: "the coupons section is not visible for customer". It was not merely hidden -
coupons could be created in the admin console but could never reach a bill. Four
separate things were broken:

  1. No public endpoint. /api/v1/coupons/** requires authentication, so a diner on the
     QR flow had no way to send a code.
  2. Cart totals hardcoded the discount to zero ("Tax and discount will be dynamic in
     future versions"), and recalculateTotals runs on every cart change, so even a
     discount set by hand would have been wiped on the next tap.
  3. Nothing linked a coupon to a cart or an order, so there was nowhere for a discount
     to live, and no record of which code had been used.
  4. CouponServiceImpl.applyCoupon incremented used_count as a side effect of merely
     CHECKING a code. A diner tapping "apply" twice burned two uses of a limited run,
     and the discount was still never stored anywhere.

Also fixed while here (pre-existing, noted in the README's limitations):
  5. CouponController had no role guard and trusted the client's restaurantId, so any
     authenticated user - including a CUSTOMER account - could list, create, edit and
     delete any restaurant's coupons.
  6. The percentage discount called BigDecimal.divide() with no scale or rounding, which
     throws ArithmeticException on a non-terminating result.
  7. A fixed-amount coupon larger than the basket produced a negative total.

Changes

  Schema (V19__link_coupons_to_carts_and_orders.sql)
    - carts.coupon_id (FK, ON DELETE SET NULL): the coupon the table is holding.
    - orders.coupon_id + orders.coupon_code: the reference plus the code as a plain
      value, so a past order stays readable if the coupon is later deleted.
    - CHECK (used_count >= 0) on coupons.

  Pure logic (new com.kashmirmenu.app.coupon package)
    - CouponPricing: validity and discount arithmetic with no side effects, used by the
      diner's preview, every cart recalculation and order placement, so all three agree.
      Explicit scale and HALF_UP rounding; discount is clamped to the basket.
    - CouponState: one value per refusal, each with the message a diner sees.

  Behaviour
    - Public POST/DELETE /api/public/tables/{qr}/cart/coupon (apply / remove).
    - Cart totals honour the held coupon, and re-check it on every change: a coupon that
      stops qualifying is dropped rather than silently discounting the bill.
    - Codes are matched case-insensitively and scoped to the table's own restaurant.
    - A use is claimed only when an order is placed, via a conditional UPDATE that
      succeeds only while a use remains, so the usage limit holds under concurrent
      checkouts. Cancelling an order releases the use (guarded against double release).
      If a coupon runs out mid-checkout the order is placed at full price rather than
      failing.
    - applyCoupon is now a read-only quote and consumes nothing.
    - Coupon endpoints restricted to ADMIN / RESTAURANT_OWNER / MANAGER, with the
      restaurant taken from the signed-in user and ownership checked on every coupon id.
    - Order and tracking responses expose the discount and the coupon code.

  Frontend
    - New CouponBox on the diner's checkout: collapsed "Have a coupon code?" prompt, a
      code field that uppercases as you type, the applied code with the saving, and a
      remove action. Refusals show the server's reason.
    - The bill's discount line names the code that produced it.
    - Order tracking shows the saving and bases the amount due on the discounted total.

Verification
  - CouponPricing: 10 unit tests written and RUN (56 pure tests now pass in total),
    covering percentage and fixed discounts, the maximum-discount cap, minimum spend and
    its shortfall message, every refusal reason, the zero-means-unlimited convention,
    non-terminating division, and the invariant that discount + payable = basket.
  - Diner coupon panel rendered in headless Chromium at 320 and 390px in all four states
    (collapsed, entry, applied, refused). No horizontal overflow.
  - CouponFlowIT written covering the whole flow, the usage limit, release on

PHASE 5 - THREE REPORTED BUGS
--------------------------------------------------------------------------------

Reported: the kitchen board showed a just-placed order as "5h 30m ago"; the diner had no
order time at all; and the order number was too long.

1. Wrong elapsed time on the kitchen board (and everywhere else)
   Cause: timestamps are stored as zone-less LocalDateTime values in the restaurant's
   business zone, and were serialised bare ("2026-10-13T14:35:00"). The browser has no way
   to know which zone such a value belongs to, so it assumes its own. Any device whose zone
   differs from the server's therefore read EVERY time out by exactly that difference -
   5h 30m being the Asia/Kolkata offset.
   Fix: new config/JacksonConfig serialises LocalDateTime with the business zone's offset
   for that date ("2026-10-13T14:35:00+05:30"), so the value is an unambiguous instant and
   is correct from any device in any zone. Deserialisation is unchanged: request bodies may
   still send a bare local date-time (the admin coupon form does).
   Frontend: new parseServerTime() accepts both forms, so nothing breaks if an old response
   is cached. lib/charts.ts now formats buckets in the timestamp's own zone, so an "8 PM"
   bucket still reads 8 PM on a device in another country.

2. No order time for the diner
   The confirmation header now shows "Ordered at 2:35 PM · 4 min ago" under the order id.

3. Order numbers were unusable
   Was "ORD-20261013-290F2080CCD3": a date plus 12 random hex characters. Unique, but a
   diner could not read it back to staff, nor staff call it across a kitchen.
   Now "ORD-1", "ORD-2", ... from a per-restaurant counter (V20 migration), with the counter
   row locked for the transaction so simultaneous orders take consecutive numbers, and the
   number reused if the order then rolls back. Existing orders keep their numbers - diners
   hold them in their browser's order history - and each restaurant's counter is seeded above
   any short number already present, so new numbers cannot collide.
   The diner header now reads "Order ID: ORD-1233" rather than just "Order ...".

Verification
  - format/charts helpers: 31 frontend tests written and RUN, including a case reproducing
    the exact bug (a timestamp 5h30m "ago" in a +05:30 offset now reads as "just now"). The
    whole suite was run under TZ=UTC, Asia/Kolkata, America/New_York and Pacific/Kiritimati
    to prove the result no longer depends on the device zone.
  - Diner confirmation header rendered in headless Chromium at 430px.
  - [NOT VERIFIED] V20 against MySQL; the Jackson serializer and the order counter were not

PHASE 13 - BUG FIX GROUP 1: CART CONCURRENCY (BUG-001, BUG-007)
--------------------------------------------------------------------------------

See FULL_STACK_BUG_AUDIT.md and BUG_FIX_PLAN.md. No schema change (highest migration is still
V25), no unrelated code touched.

Root cause
  Cart operations were not serialised per table. The cart belongs to a TABLE, not a person, and the
  QR flow is unauthenticated, so two phones at one table are two concurrent writers by design.

  Three races, not the two the audit reported:
    1. placeOrder read the ACTIVE cart with no lock and set CHECKED_OUT as its last statement, so a
       double-tap produced two orders, double stock deduction and two coupon claims.
    2. getOrCreateActiveCart had a find-then-insert race. carts has NO unique constraint on
       (restaurant_table_id, status), so two concurrent first requests each inserted an ACTIVE cart;
       findByRestaurantTableAndStatus then matched two rows and threw on every later read - a
       PERMANENT 500 for that table. Found while implementing the fix; worse than BUG-001 and not in
       the audit.
    3. Concurrent cart mutations could compute totals from a basket missing the other's item.

Fix
  The lock is on restaurant_tables, not on carts. A pessimistic lock on a SELECT matching no rows
  locks nothing, so locking the cart cannot prevent race 2; the table row always exists and every
  cart operation already loads it.
  - RestaurantTableRepository: findByQrIdentifierForUpdate / findByIdForUpdate (PESSIMISTIC_WRITE).
  - CartServiceImpl.getRestaurantTable now takes the lock, so all cart paths serialise through one
    place. Reads take the write lock too: a read-only variant would be cheaper, but two helpers
    differing only in locking are easy to mix up and the lock is held for milliseconds.
  - OrderServiceImpl.placeOrder locks the table FIRST, then reads the cart, so the second of two
    checkouts waits and is then refused with the existing "No active cart found".

  Documented lock order: restaurant_tables -> coupons -> order counter -> inventory. Reordering in
  one place is enough to deadlock two checkouts at different tables on the shared inventory rows.

Impact on existing behaviour
  - Cart operations serialise per table (intended). No API, DTO or UI change.
  - A duplicate submit now fails cleanly instead of double-ordering.
  - NOT added: a unique index on (restaurant_table_id, status). It would be belt-and-braces but is a
    schema change, which was not approved. The lock is sufficient on its own.

Tests added: CartConcurrencyIT - five cases with a latch-based helper that releases threads together
(starting them sequentially often lets the first finish before the last begins, which would pass
falsely). Covers: one order from two simultaneous checkouts; stock moved once; coupon claimed once;
four simultaneous first requests produce one cart and a subsequent read returns 200; concurrent adds
both land with a subtotal matching the lines.

Verification
  - EXECUTED: Java syntax clean; a lock-order checker across all multi-lock methods (including
    cross-file inventory locks via StockService) confirms every path follows the documented order;
    authorization/platform/entity-migration verifiers clean; migration ordering clean; 61 pure Java
    and 31 frontend logic tests still pass.
  - [NOT VERIFIED] CartConcurrencyIT has NOT been run - ./gradlew cannot resolve Gradle in this
    environment. The tests that prove this fix are precisely the ones that could not be executed.

PHASE 20 - DATABASE AUDIT REMEDIATION, STEPS 4-5 (DB-02, DB-03, DB-07, DB-10)
--------------------------------------------------------------------------------

Completes the database audit except DB-06, which is deliberately left alone (below).

DB-07 - one active cart per table is now a database guarantee (V28)
  The application already serialises cart operations by locking the table row, but the database still
  permitted two ACTIVE carts per table - and if one ever appeared, findByRestaurantTableAndStatus
  would match two rows, fail to fit an Optional, and throw on EVERY later cart read for that table.
  MySQL has no partial indexes, so uniqueness is expressed through a STORED generated column that is
  NULL unless the cart is ACTIVE; NULLs do not collide, so any number of CHECKED_OUT carts stay legal.
  This also gives that lookup an index it never had. The migration documents the duplicate-detection
  query to run if it fails to apply.

DB-02 - the coupon lookup can now use its unique index (V29)
  upper(c.code) = upper(:code) wrapped the indexed column in a function, so the code half of
  UNIQUE (restaurant_id, code) was unusable. Codes are now normalised on write (V29 upper-cases
  existing rows) and the query is a plain equality. One CouponCode.normalise() is the single place
  that normalisation happens, so the write path and all read paths cannot drift - the old query
  tolerated any input precisely because it could not use the index.
  Locale.ROOT, not the default locale: in a Turkish locale "diwali".toUpperCase() produces a dotted
  capital I and the same code would normalise differently depending on where the server runs.

DB-03 - the audit search no longer defeats its own indexes
  Replaced the ":param is null or ..." JPQL with AuditSpecifications, which adds only the predicates
  actually supplied, so idx_audit_action and idx_audit_time can be used. The email filter is now a
  PREFIX match ('alice%') rather than a substring ('%alice%'): a leading wildcard cannot use an index
  at all, and searching by the start of an address covers the realistic case. audit_log is one of
  only two unbounded-growth tables here, so this was the finding most likely to worsen unattended.

DB-10 - websocket publish moved to after commit
  Was inside the notification transaction. Two problems, the first being correctness rather than
  performance: a notification was sent for work that might still roll back, so an order whose stock
  check then failed had already told the kitchen it was coming. Second, it was network I/O holding a
  database connection - in placeOrder's case while the table, coupon, counter and inventory locks were
  all still held. Now registered as an afterCommit synchronisation, falling back to publishing
  immediately when no transaction is active.

DELIBERATELY NOT FIXED: DB-06 (per-restaurant checkout serialisation on the order counter)
  Every concurrent checkout in a restaurant queues on one counter row. The fix options all trade
  something real - readable sequential numbers, or gap-free numbering - and the cost depends entirely
  on actual throughput. Changing lock scope on the hottest write path without measurement would be
  guesswork. Watch hikaricp_connections_pending and checkout latency during the k6 baseline: if
  latency rises with concurrent VUs while CPU stays flat, this is why.

Verification
  - EXECUTED: CouponCode.normalise compiled and run under a TURKISH locale - 7/7, including the
    dotted-I case that a naive toUpperCase() gets wrong. Java syntax clean; migration ordering clean
    (29); every table referenced by V27-V29 is created in an earlier migration; no index-defeating
    predicate (upper() on an indexed column, leading-wildcard LIKE, OR-null filter) remains in
    executable code; paging guard clean; all kitchen list reads batch; OrderStatusPolicy 31/31;

WHAT THE EVIDENCE NOW SAYS
  CartConcurrencyIT now fails at its ASSERTIONS (lines 188/209/233), not at setup, so placement
  reaches the assertions there. Each asserts a count that should be 1 (orders created, stock moved,
  coupon claimed). If the lock were broken I would expect 2; if placement fails entirely, 0. A single
  cause that fits every failing class is: placement is failing for every caller, and the concurrency
  tests merely report created == 0.

  Of everything placement touches, one thing is new, load-bearing, and untested by any earlier passing
  test: RestaurantOrderCounter - the ONLY entity in the codebase with an assigned id (every other uses
  @GeneratedValue), and with no @Version. In the test profile Flyway is off, so V20's backfill never
  ran and NO counter row exists; every placement therefore takes the orElseGet(create) branch and
  calls save() on an assigned-id entity. Spring Data cannot tell such an entity is new, so it chose
  merge() - a SELECT then INSERT - for a row the code knows it is creating.

FIX (a hypothesis, stated as one)
  RestaurantOrderCounter now implements Persistable<Long>, tracking a transient `persisted` flag set
  by @PostPersist/@PostLoad, so isNew() is answered rather than guessed. The flag is named for what it
  records and excluded from Lombok's @Getter/@Setter, so no clashing accessor is generated and only
  lifecycle callbacks change it.
